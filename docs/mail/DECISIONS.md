# Code + Mailbox decisions

One line each. Made during the unattended v1 build; revisit any of them.

- Mail data lives in its own SQLite file (`<state>/mail/mail.sqlite`) with its own migrations. The orchestration database also indexes completed provider turns for the weekly usage meter.
- Mail threads are not orchestration threads. A mailbox has thousands of threads; the shell stream would carry all of them. Mail keeps its own thread table and sidebar states.
- A mail thread's chat session (L2) is a real T3 thread, created lazily the first time the user asks the AI about that email, in one hidden "Mail" project per environment rooted at `<state>/mail/workspace` (which holds EMAIL.md). This gives the model picker, subagents and the normal composer for free.
- The coding sidebar, project pickers and command palette hide the Mail project; the Mail tab shows its sessions inside mail threads.
- IMAP library: `imapflow` (IDLE, CONDSTORE/QRESYNC, X-GM-*, UIDPLUS). SMTP: `nodemailer`. No MIME parser dependency: bodies come from the text part via IMAP `download`, cleaned by our own small HTML-to-text. The reader separately fetches and caches the formatted MIME alternative when a message comes into view.
- Gmail syncs `[Gmail]/All Mail` only and reads `\Inbox`/`\Sent` from X-GM-LABELS, so one connection and one IDLE cover incoming and sent mail. Other providers sync INBOX (IDLE) plus the Sent folder (polled).
- A Gmail message that loses `\Inbox` outside T3 (archived on the phone, or a filter skipped the inbox) settles its thread with reason "archived". We follow the user's Gmail, never fight it.
- Server mirroring (archive on settle) defaults to off so a first run cannot rearrange a real mailbox; it is one switch in Mail settings.
- Delete always moves the thread to the server Trash, because the user asked for it directly; mirroring governs only settle. The thread leaves the local store at once, and undo finds the messages in Trash by Message-ID (their UIDs change there) and moves them back to the inbox, where sync ingests them again.
- The reader shows only the formatted or full message. The cleaned text still feeds triage and chat context, but it was not readable enough to offer as a view.
- Formatted mail opens in Reader view: a local, deterministic rebuild of the sanitized HTML from a few elements, rendered in the app (not the iframe) with T3's markdown styles. It keeps every visible word and every http/https/mailto link (a picture link gets its alt, its title or its host as text), drops what inline styles truly hide (a child can restore a zero font size or hidden visibility, so those are tracked per text node), styles and images, keeps a short multi-cell row on one line (an item and its price) and keeps header or column grids as tables with captions and spans. No model decides what to keep. Mail with 3+ pictures (tracking pixels excluded) and under 200 characters of current text (folded history excluded) opens in the original, since its message is the pictures.
- App passwords go in the OS keychain through `@napi-rs/keyring` (already a server dependency). If no keychain is available (headless Linux), they fall back to T3's 0700 secrets directory and the account shows that.
- L1 runs through a new `generateMailTriage` text-generation operation so every provider adapter makes an explicit decision; fx, Kiro and ACP-registry report it unsupported like other text operations.
- L1 batches up to 12 threads per call, debounced 2 s after a sync burst; the newest message of each thread is cleaned and cut to 1,200 characters; older messages contribute only their sender and first line, except up to 3 earlier messages that arrived since the last review, which go in whole so a burst ("shipped", "out for delivery", "delivered") is judged together.
- Escalation: a verdict under 0.6 confidence, or from a sender on the "people you've replied to" list, re-runs with the escalation model when one is set; otherwise it stays a suggestion.
- Nothing settles on its own without a rule the user saved. Approval streaks that graduated a sender or category were dropped: settling three shipping notices says nothing about the delivered one, and neither a sender nor a category can tell them apart. Approvals and dismissals still reach the model as facts keyed `sender:<address>` and `category:<name>`.
- A rule's scope (from, domain, subject, list) is enforced by the server. Its optional "when" is plain language the model checks in the same L1 call: each email lists only its in-scope rules under per-email keys (`r1`…), so the model can only pick a rule the server already scoped. A rule without "when" skips the model. A rule with "when" may have no scope and then covers all mail, at a prompt cost on every email.
- A rule is the user's firm choice: it settles whatever it covers, money and security mail included, with no second opinion from guardrails. Rules only settle: holding mail in Active is the default, so a keep rule had nothing to do. An unclear match or low confidence stays a suggestion.
- Agents can add, change and delete rules through MCP (`t3_mail_rule`), live at once, because a rule the user asked for in chat is useless if they must confirm it again. The rule records which agent added it until the user saves it themselves. The tool is told to act only on what the user asks; email text in its context stays data.
- Undo reverses only its own action's trust effect (one approval or one rejection) on the keys recorded at the time, so later approvals and a sender change on the thread are kept.
- Guardrails (replied-to people, urgent wording, money/invoices, security alerts, legal) only label why an email may matter, in its triage history. They read the whole cleaned message, not the model's 1,200-character cut.
- Nothing auto-settles when the newest message's body could not be downloaded (after 3 tries), except under a rule without a condition; it stays a suggestion.
- The model reads every email. Only the user's exact choices skip it: rules without a condition and senders with AI turned off.
- Each verdict stores the model's one-line reason and the provider instance and model that made it, so rows show that model's icon and the recap and chat say why. The reason is capped at 140 characters because it travels with every sidebar row.
- Senders with AI off (an address, or a domain with its subdomains) skip model triage. An unconditional user rule can still settle their mail. The list is read again right before each model call, since it can change while a batch waits. Mail chat gets no content for them, `t3_mail_read` refuses their threads, mail tools mask their subjects, other messages from them are masked wherever a thread is sent to a model, and voice notes skip mail sent to them because replies quote what they answer. Turning AI on removes the exact entry, so lifting a domain is explicit.
- A model settle without a reason stays a suggestion: the reason is what lets the user check an automatic settle. Reasons are shown only while the triage they came from is current and still describes the thread's state.
- Settle reasons (fyi, receipt, noise…) stay internal: the model returns them and the chat history names them, but the UI shows only who decided (model icon or rule) and the one-line why. A label the user can't change reads like a setting to manage.
- Auto-settle uses the same rules in the reader and in Settings. An exact sender scope with no condition settles future mail from that address.
- Replying settles the thread with reason "replied". If the reply asks a question, the thread goes to Working (waiting on their reply) instead, and a nudge returns it to Active after the configured days.
- Email lists show the latest message first, including paginated settled history. Snoozed uses the next wake time.
- The weekly Mail budget adds character-based estimates for triage, escalation and voice notes to the input and output tokens providers report for finished Mail chat turns. Partial turns contribute their known counters. The default cap is 300k tokens. Mail Settings compares this amount with T3’s recorded provider usage for the same environment and local calendar week. Opening the meter requests the usage summary.
- The daily recap is computed locally from the action log in SQL (no model call) and shown at the top of the Mail home once per day. It lists the AI and rule settles from the last day that are still settled, newest first; "Bring back" is the settle's undo, which the model also hears about.
- Mobile Mail is Later per the spec (iOS app); contracts and client-runtime state are shared so mobile can add the tab without server changes.
- Opening an email chat materializes saved triage decisions without launching a model turn. The ordinary composer supplies scoped mail context when the user asks a question.
- Mail chat sessions start in approval-required mode: the agent can read mail and leave drafts through MCP, but shell or file edits still ask first, since an email is untrusted input.
- First sync fetches the newest 200 messages plus (on Gmail) the newest 200 inbox messages. Backfill brings older mail in settled, except inbox mail from the last 30 days, which stays Active.
- Connecting a busy account must not spend a week of tokens before the user has seen anything, so a thread whose newest incoming message predates the account is held (`triage_state = held`) at the point triage would call the model. It is decided by date, not by which sync fetched it, so rebuilds, search hits and databases from before this rule behave the same; rules and AI off still apply first. The user sends held Active mail to AI from Mail home (`review`, up to the count shown, sorted after new mail). Anything a review can't finish (Stop, the cap, a failed call) goes back to held, and each batch rechecks that its mail is still in review before the call and before its verdicts apply.
- EMAIL.md is loaded into prompts by section: triage compiles preference bullets and skips tone and signature. Chats get tone, standing preferences, priorities and sections matching the sender. Each view is capped at 1,500 characters.
- RPC scopes: reads use the orchestration read scope; acting on mail, drafts, send and sessions use operate; accounts, settings and EMAIL.md writes use settings-write.
- Nudges are stored as short codes (`waiting:N`, `unanswered:N`) and rendered by the client, so the server never stores translated copy.
- A mail session that ends without leaving a draft returns its thread from Working to Active on the next minute tick.
- With server mirroring on, a reply sent from T3 archives the thread on the server like any other settle; replies sent from another client leave the server copy where that client put it.
- Sending approves one draft revision: every save bumps it, and send carries the revision the user saw. A draft keeps its Message-ID across retries. A failure that may have reached the server (connection lost mid-send, or a restart while sending) says "It may have been sent; check Sent" instead of retrying on its own.
- IMAP and SMTP require TLS (implicit or STARTTLS) except on loopback, where the local test server runs.
- Model calls for mail run outside the lock that serializes user actions; a verdict is discarded if new mail reached the thread while the model ran, and failed or capped triage retries every 10 minutes.
- Mail model calls run with an empty working folder (`<state>/mail/model`) because some harnesses (OpenCode) keep a read tool on for text generation.
- Mail home offers up to 50 visible suggestions per approval batch so the user can review precisely what the button will settle.
- Mail arrival notifications report only a count and skip initial sync and backfill. The coding view subscribes without downloading a mailbox snapshot.
- Learned draft edits are retrieved by account and correspondent. Related-mail lookups use the same account boundary.
- Archive and read operations capture the affected messages at the time of the action. Undo checks the current revision or field value before reversing a change.
- Automatic mail generation uses the selected provider instance. When it is unavailable, mail content stays local until the selected provider can run.
- An approval names the revision of each visible suggestion. If a reply or a new proposal changes any of them, the batch must be reviewed again.
- Partial SMTP acceptance keeps a delivery record and creates a new revision of the same draft for the rejected recipients. Sending it requires another approval.
- Body download quota responses pause downloads and backfill for 24 hours. New message headers continue to sync, and completed body downloads in the same batch are retained.
- Rows and headers show the email's own subject. L1 no longer writes a summary line: model summaries hid the descriptive subjects senders already write, and dropping them shortens every triage reply.
- Sync downloads the formatted body of mail in Active, Working, Snoozed, Pinned, and anything settled in the last 14 days. The reader shows nothing for a message until its formatted body is known, then the formatted email or, when there is no HTML part, the plain text, so raw text never flashes first.
- A draft records the message it answers and whether it is a reply or a forward. That message sets In-Reply-To and References, and its formatted body is quoted (or forwarded with its attachments) at send time, so the draft stores only what the user typed and an agent never has to copy the original. If that message leaves the thread, sending fails rather than answering another one. Drafts saved before targets existed have none and send exactly as written.
- Reply and Reply all are the same draft mode; the recipients the user kept are the difference. Reply-To wins over From for the reply address. Reply-To is backfilled from the server envelope for mail synced before it was stored.
- A forward settles the thread as "done", not "replied": the user passed the email on, so the thread must not claim the sender was answered.
- A new email is its own thread (`<account>:n:<uuid>`) with no messages and one draft, held in Working so nothing hands it to Active. Ingest checks Message-IDs against these threads before using Gmail's thread id, so the server's copy and replies join it. Deleting one discards its draft and removes the thread; undo restores both.
- A thread with no incoming mail is named by the first recipient of its newest message, so Drafts and Sent show who it went to.
- Trash lists delete actions from the last 30 days that were not undone, labelled from the subject and sender stored with the delete. Mail does not sync the server's Trash, so mail deleted in another client is not listed.
